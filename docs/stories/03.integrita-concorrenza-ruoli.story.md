# Conferimenti, uscite e registro coerenti sotto concorrenza; ruoli operativi con abilità

## Story

Come **responsabile tecnico dell'impianto**
voglio che **accettazioni, uscite e registro restino coerenti anche con più operatori e palmari insieme, e che ognuno possa fare solo ciò che il suo ruolo prevede**
così da **non avere carichi doppi sul registro legale, FIR e movimenti con pesi diversi, né operatori che spediscono o accettano senza averne titolo**.

## Perché / evidenze (audit 2026-11-05)

| Rilievo | Evidenza | Effetto |
| --- | --- | --- |
| database R2 | `AcceptDeliveryAction`, `RejectDeliveryAction`, `ReceiveDeliveryAction` controllavano lo stato fuori transazione | doppio carico di registro e doppie unità con richieste concorrenti |
| database R3 | `GetLotLoadEntryIdsAction` senza `effective()` | dopo una rettifica ogni scarico dei lotti falliva |
| database R6/R7, funzionale | unità caricate non riservate; righe lette prima della transazione | registro/FIR con kg diversi dal movimento; righe escluse dalla spedizione |
| funzionale | etichetta `/l/LOC-…` senza identificatore | stoccaggio da palmare impossibile |
| database R5 | `whereIn` con tutti gli id storici | errore a 65.535 parametri, form di ricezione bloccato |
| sicurezza M6/B4, database R12 | numero RENTRI modificabile dal cliente, scope ricalcolato per riga | dati regolatori alterabili, N+1 |
| funzionale | FIR `draft` (default UI) → accettazione fallita | percorso principale interrotto |
| funzionale | chiave lang `shipment_header` vs file `create_shipment_header.php` | modale "Nuova uscita" con chiavi grezze |
| funzionale | `inputmode="none"` | impossibile digitare un codice dal telefono |
| funzionale 1.4 | "Aggiungi input"/"Registra output" di Processing | consumi/prodotti senza registro e senza lotto |
| database R17 | quote sovrascritte nel diamante | origine del lotto sbagliata |
| database R13/R14 | query per riga nelle tabelle; `arrived_at` senza indice | pagine lente al crescere dei dati |
| sicurezza A2/A3/M4 | abilità non dichiarate consentite, azioni custom senza `authorize`, permessi mai seminati | chi legge scrive; nella pratica tutti super-admin |

## Acceptance criteria

1. Accettazione/respingimento con istanza stantia falliscono sulla transizione: nessun lotto, unità o carico in più. ✔ `DeliveryConcurrencyTest`
2. Un FIR ha al più un conferimento vivo (unique su `deliveries.open_fir_id`); FIR in stato finale non si conferisce. ✔
3. FIR `draft`/`issued`/`in_transit` portato a `delivered` in ricezione; l'accettazione riesce. ✔
4. Dopo la rettifica del carico, lo scarico del trattamento riporta `load_entry_ids = [rettifica]`. ✔ `RectifiedLoadTest`
5. Unità caricata → `reserved`; tolta/uscita annullata → `stored`; riservata non si sposta, non si tratta, non si carica altrove; dopo una rettifica movimento = scarico = FIR. ✔ `ShipmentReservationTest`
6. `/l/LOC-{magazzino}-{codice}` (anche con trattini, CR/LF, URL assoluto) risolve la posizione; `SU-…` senza identificatore risolve l'unità. ✔ `ScannedCodeTest`
7. Nessuna query con parametri proporzionali alla storia (giacenza per EER, select FIR, conferimenti cliente). ✔ `UnboundedQueriesTest`
8. Numero RENTRI del cantiere bloccato dopo il primo FIR, anche lato server; kg per cantiere in una query; scope cliente memoizzato. ✔
9. Ogni Filament action di Roosko trova il suo file lang. ✔ `ActionLangKeysTest`
10. Diamante: quota dell'origine = somma dei cammini. ✔ `LotOriginDiamondTest`
11. Tabelle conferimenti, lotti, uscite: stesse query con 1 e 4 record. ✔ `AdminTablesQueryCountTest`
12. Policy con `DeniesUndeclaredFilamentAbilities`; azioni custom con abilità; seeder idempotente di permessi e ruoli; operatore non vede Accetta/Respingi, accettazione sì. ✔ `AuthorizationTest`
13. Roosko spegne le azioni native sul materiale di Processing. ✔ `ProcessingMaterialActionsTest`

## Dev agent record

- 2026-11-05/06 — Claude (Roosko).
  - **Decisioni**:
    - lock prima di tutto dentro `RunInPlantTransactionAction` e ricontrollo sui dati bloccati; l'istanza passata dal chiamante si riallinea con `setRawAttributes` (niente stato duplicato);
    - "un FIR = un conferimento" con colonna **generata virtuale** (`case when status <> 'rejected' and deleted_at is null then fir_id end`) e unique: consente un nuovo arrivo dopo respingimento o eliminazione, funziona su MySQL e sqlite;
    - FIR in bozza: avanzamento in ricezione (scelta del dominio Roosko: il camion è arrivato), invece di cambiare il default della UI di Waste;
    - riserva dell'unità con lo stato `reserved` già previsto da Warehouse (nessuna action nuova in Warehouse): azioni in Roosko con `LockStockUnitAction`;
    - la spedizione usa i kg del movimento e riallinea `shipment_items.quantity_kg`: una sola fonte (il peso dell'unità sotto lock);
    - numero RENTRI del cantiere: bloccato dopo il primo FIR (non subito: il cliente lo inserisce alla creazione); `is_active` resta del cliente (dato operativo);
    - ruoli operativi `roosko.*` con permessi; l'accesso ai pannelli resta ai ruoli `{modulo}::admin` (`BaseUser::canAccessPanel`), documentato;
    - nel pannello amministrativo di Roosko (tenant-aware dal commit `2868288`) i test Livewire impostano un tenant.
  - **Verifica**: harness `/home/claude/harness` (PHP 8.4, Laravel 13, Filament 5). Pest Roosko: 58 passati prima, 117 passati dopo. PHPStan su `Modules/Roosko/app`: 0 errori. `check_refs.php`: 0 riferimenti non risolti.
  - **Rischi residui**:
    - con database davvero separati l'atomicità resta best-effort (niente 2PC); lo unique `open_fir_id` resta la difesa;
    - il retry su deadlock rilancia il callback: le action dentro la transazione non devono avere effetti esterni (oggi è così: code e RENTRI dopo il commit);
    - `Delivery` respinta o eliminata con `open_fir_id` NULL: se si ripristinasse un conferimento eliminato con un altro vivo sullo stesso FIR, il ripristino fallirebbe sull'unique (voluto);
    - i limiti di capacità e autorizzazione (R4) restano check-then-act nel guard di Roosko: lock su `authorized_wastes` da fare.
